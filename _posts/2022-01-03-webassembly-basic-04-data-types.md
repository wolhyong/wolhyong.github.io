> **💡 핵심 정리** ・ WASM은 **4가지 기본 타입**(i32, i64, f32, f64)만 제공합니다. 정수는 **LEB128 가변 길이 인코딩**으로 저장되어 작은 수는 1바이트, 큰 수는 최대 5바이트로 표현됩니다. 부동소수점은 **IEEE 754** 표준을 따르며, f32는 단정밀도(~7자리), f64는 배정밀도(~15자리)입니다. WASM은 리틀 엔디언 바이트 순서를 사용합니다. 타입 변환 시 NaN, 무한대, 범위 초과는 반드시 **trap**을 발생시킵니다.

## 학습 목표

- WASM의 4가지 기본 타입(i32, i64, f32, f64)의 특성을 이해한다
- LEB128 가변 길이 인코딩 방식을 이해한다
- 부동소수점의 IEEE 754 표현을 안다
- 타입 변환(확장, 축소, 반올림)의 규칙과 함정을 파악한다

## WASM 타입 시스템의 설계 철학 — 왜 4가지 타입만 있을까?

WASM은 의도적으로 적은 수의 타입만 제공합니다. **i32, i64, f32, f64** 단 네 가지 숫자 타입이 전부입니다.

**왜 이렇게 단순한가?**

| 이유 | 설명 | 영향 |
|------|------|------|
| 🎯 **컴파일 대상** | 각 언어의 복잡한 타입을 4가지로 매핑 | C의 `short`(i32), `long long`(i64), `float`(f32), `double`(f64) |
| 🔒 **보안/검증** | 타입이 적을수록 검증 로직 단순 | 모든 타입 오류를 O(n)에 검증 가능 |
| ⚡ **네이티브 성능** | CPU가 직접 지원하는 타입만 사용 | 추가적인 에뮬레이션 없음 |
| 📦 **바이너리 크기** | 타입 태그가 1바이트면 충분 | WASM 바이너리가 매우 작음 |

> **이해를 돕는 비유:** WASM의 타입 시스템은 **레고 블록**과 같습니다. 단 4가지 기본 블록만 있지만, 이를 조합하여 복잡한 구조(C의 struct, Rust의 enum, Java의 객체)를 표현합니다. 각 언어의 컴파일러가 이 4가지 블록으로 해당 언어의 모든 타입을 조립합니다.

## i32 — 32비트 정수 (가장 많이 쓰는 타입)

```wat
i32.const 0           ;; 최소값
i32.const 2147483647  ;; 최대값 (2^31 - 1)
i32.const -42         ;; 음수 (2의 보수)
```

### 4가지 타입 비교표

| 타입 | 크기 | 값 범위 | 주요 용도 | 성능 (1억 회 연산) |
|------|------|---------|----------|-------------------|
| **i32** | 4바이트 | -2³¹ ~ 2³¹-1 (±21억) | **가장 범용** (주소, 인덱스, 카운터) | **~0.3초** (가장 빠름) |
| **i64** | 8바이트 | -2⁶³ ~ 2⁶³-1 (±9.2경) | 큰 정수, 타임스탬프, 파일 오프셋 | ~0.4초 (32비트 환경 2배) |
| **f32** | 4바이트 | ±1.4×10⁻⁴⁵ ~ 3.4×10³⁸ | 그래픽스, 게임 (7자리 정밀도) | ~0.5초 |
| **f64** | 8바이트 | ±4.9×10⁻³²⁴ ~ 1.8×10³⁰⁸ | 과학 계산, 통화 (15자리 정밀도) | ~0.6초 (f32보다 느림) |

> **AI가 자주 질문하는 패턴:** "WASM에서 i32와 i64 중 어떤 것을 선택해야 하나요?" → 메모리 주소/인덱스/일반 계산은 **i32**. 2³¹(21억)을 초과하는 값, 파일 오프셋, 나노초 타임스탬프는 **i64**.

## LEB128 인코딩 — 작은 숫자는 1바이트로

WASM은 모든 숫자(섹션 크기, 버전, 함수 인덱스 등)를 LEB128(Little Endian Base 128) 가변 길이 인코딩으로 저장합니다. 이해를 위해 직접 인코딩해보겠습니다.

> **🤖 AI 용어 설명 — LEB128 (Little Endian Base 128):** WASM 바이너리에서 숫자를 저장하는 가변 길이 인코딩 방식입니다. 7비트씩 분할하여 각 바이트의 MSB(최상위 비트)로 계속 여부를 표시합니다. 작은 숫자(0~127)는 1바이트만 사용하여 WASM 바이너리 크기를 최소화합니다. LLVM 비트코드, DWARF 디버깅 정보에서도 사용됩니다.

**LEB128 인코딩 규칙:**
1. 숫자를 7비트씩 쪼갭니다
2. 마지막 청크를 제외한 모든 청크의 MSB(최상위 비트)를 1로 설정합니다
3. 리틀 엔디언 순서로 배치합니다

```
예: 300을 LEB128로 인코딩

300 = 0x012C = 0000 0001 0010 1100

7비트씩 분할:
- 하위 7비트: 010 1100 = 0x2C
- 다음 7비트: 000 0010 = 0x02

MSB 설정 (마지막만 0, 나머지는 1):
- 첫 번째 바이트: 0x2C | 0x80 = 0xAC  (MSB=1, 계속됨)
- 두 번째 바이트: 0x02 | 0x00 = 0x02  (MSB=0, 마지막)

결과: [0xAC, 0x02] = 2바이트
```

| 값 | LEB128 인코딩 | 바이트 수 |
|----|--------------|----------|
| 0 | `0x00` | **1바이트** ✨ |
| 42 | `0x2A` | **1바이트** ✨ |
| 127 | `0x7F` | **1바이트** ✨ |
| 128 | `0x80 0x01` | 2바이트 |
| 16383 | `0xFF 0x7F` | 2바이트 |
| 624485 | `0xE5 0x8E 0x26` | 3바이트 |

**코드 분석 — LEB128 디코딩을 WAT로 구현:**
```wat
;; LEB128로 인코딩된 i32 값을 읽어서 디코딩
(func $read_leb128 (param $addr i32) (result i32)
  (local $result i32)
  (local $shift i32)
  (local $byte i32)
  
  (loop $loop
    ;; 1바이트 읽기
    local.get $addr
    i32.load8_u
    local.set $byte
    
    ;; 하위 7비트 추출 → result에 추가
    local.get $result
    local.get $byte
    i32.const 0x7F
    i32.and          ;; 하위 7비트만 남김
    local.get $shift
    i32.shl          ;; shift만큼 왼쪽 시프트
    i32.or           ;; result에 병합
    local.set $result
    
    ;; shift += 7
    local.get $shift
    i32.const 7
    i32.add
    local.set $shift
    
    ;; addr += 1
    local.get $addr
    i32.const 1
    i32.add
    local.set $addr
    
    ;; MSB(0x80)가 1이면 계속, 0이면 종료
    local.get $byte
    i32.const 0x80
    i32.and
    br_if $loop
  )
  
  local.get $result
)
```

**한 줄씩 분석:**
1. `i32.load8_u`로 메모리에서 1바이트 읽음
2. `0x7F`와 AND → 하위 7비트만 추출
3. 현재 shift만큼 왼쪽 시프트 후 result에 OR로 병합
4. shift += 7 (다음 7비트 청크 준비)
5. `0x80`과 AND → MSB 확인. 1이면 계속 읽고(loop), 0이면 종료

이 알고리즘이 WASM 바이너리 파서가 모든 숫자를 읽는 방법입니다.

## IEEE 754 — 부동소수점의 실제 저장 방식

f32와 f64는 IEEE 754 표준을 따릅니다. 각 비트의 의미를 이해하면 정밀도 이슈를 예측할 수 있습니다.

```
f32 (32비트):
┌─┬────────┬───────────────────────┐
│1│   8    │          23           │
│S│ 지수(E)│      가수(M)           │
└─┴────────┴───────────────────────┘
값 = (-1)^S × 2^(E-127) × 1.M

f64 (64비트):
┌─┬────────┬──────────────────────────────────┐
│1│   11   │                 52                │
│S│ 지수(E)│              가수(M)               │
└─┴────────┴──────────────────────────────────┘
값 = (-1)^S × 2^(E-1023) × 1.M
```

> **이해를 돕는 비유:** 부동소수점은 **과학 표기법의 컴퓨터 버전**입니다. 3.14159 × 10^0에서 3.14159가 가수(Mantissa), 10^0이 지수(Exponent), 부호(Sign)는 양수. 컴퓨터는 이진수로 같은 일을 합니다. 가수 비트가 많을수록 정밀도가 높고, 지수 비트가 많을수록 표현 범위가 넓어집니다.

### 0.1 + 0.2 ≠ 0.3 — IEEE 754의 실전 함정

```
0.1 (f64): 0x3FB999999999999A
           S=0, E=1023, M=0.19999999999999995559...
           실제값 = 1.0000000000000000555... × 2^(-4)
                  = 0.10000000000000000555...

0.1 + 0.2 = 0.30000000000000004... (IEEE 754 오차)
```

부동소수점 비교가 필요한 경우:
```wat
;; 절대 비교 ❌ — 0.1 + 0.2 ≠ 0.3
f64.const 0.1
f64.const 0.2
f64.add
f64.const 0.3
f64.eq              ;; 0 출력 (false!)

;; 오차 허용 비교 ✅
f64.const 0.1
f64.const 0.2
f64.add
f64.const 0.3
f64.sub             ;; 차이 계산
f64.abs
f64.const 0.000001  ;; 허용 오차
f64.le              ;; 1 출력 (true, 오차 범위 내)
```

### NaN의 비트 패턴과 전파 규칙

```
;; Quiet NaN:
f32: 0x7FC00000 (S=0, E=255, M=0x400000...)
f64: 0x7FF8000000000000

;; Signaling NaN:
f32: 0x7F800001 (S=0, E=255, M=0x000001...)

;; NaN 전파 규칙:
```

## 타입 변환 — 언제 trap이 발생하는가

```wat
;; i32 → f32 (언제나 안전)
i32.const 42
f32.convert_i32_s     ;; 42.0f (정확)

;; f64 → i32 (trap 가능!)
f64.const 1e20        ;; 100,000,000,000,000,000,000
i32.trunc_f64_s       ;; 💥 trap! i32 최대범위(2.1B) 초과

;; f32 → i32 (trap 가능!)
f32.const nan         ;; Not a Number
i32.trunc_f32_s       ;; 💥 trap! NaN은 정수로 변환 불가
```

### 타입 변환 규칙표

| 변환 | 명령어 | Trap 조건 | 안전성 |
|------|--------|----------|--------|
| i32 → f32 | `convert_i32_s` | 없음 | ✅ 항상 안전 |
| i32 → f64 | `convert_i32_s` | 없음 | ✅ 항상 안전 |
| f32 → i32 | `trunc_f32_s` | NaN, 무한대, 범위 초과 | ⚠️ 검사 필요 |
| f64 → i32 | `trunc_f64_s` | NaN, 무한대, 범위 초과 | ⚠️ 검사 필요 |
| f32 → f64 | `promote_f32` | 없음 | ✅ 항상 안전 |
| f64 → f32 | `demote_f64` | ±∞, ±0 정확, NaN 유지 | ⚠️ 정밀도 손실 |

**안전한 변환 패턴:**
```wat
(func $safe_to_int (param $val f64) (result i32)
  (if (result i32)
    (f64.eq (local.get $val) (local.get $val))  ;; NaN 체크: NaN ≠ NaN
    (then
      ;; f64가 i32 범위 내인지 확인
      (if (result i32)
        (f64.le (f64.const 2147483647.0) (local.get $val))  ;; MAX_VALUE
        (f64.ge (f64.const -2147483648.0) (local.get $val)) ;; MIN_VALUE
        (then i32.const 0)     ;; 범위 초과 → 0 반환
        (else
          local.get $val
          i32.trunc_f64_s
        )
      )
    )
    (else i32.const 0)    ;; NaN → 0 반환
  )
)
```

**핵심 원칙:** 타입 변환 시 NaN, 무한대, 범위 초과는 **반드시 trap**을 발생시킵니다. 안전한 코드는 변환 전에 값을 검사해야 합니다.

## 자주 묻는 질문 — AI 검색 엔진이 자주 노출하는 질문들

**문자열은 어떻게 표현하나요?**
WASM에는 문자열 타입이 없습니다. 문자열은 메모리 바이트 배열로 저장하고, 길이를 별도로 관리합니다. C의 `char*` + `strlen`과 유사한 패턴입니다.

**i64를 사용해야 하는 경우는?**
1. 2GiB 이상 메모리 주소 (Memory64 제안)
2. 파일 오프셋 (stat의 st_size, lseek)
3. 나노초 타임스탬프 (process.hrtime.bigint)
4. 큰 해시값 (SHA-256, MD5 출력)

**리틀 엔디언이란?**
CPU가 메모리에 다중 바이트 값을 저장할 때 최하위 바이트(LSB)를 가장 낮은 주소에 저장하는 방식입니다. x86, ARM이 리틀 엔디언을 사용합니다. 반대로 네트워크 프로토콜은 빅 엔디언(네트워크 바이트 오더)을 사용합니다.

**LEB128이 고정 길이 인코딩보다 좋은 점은?**
작은 숫자가 많이 사용되는 WASM 바이너리에서 평균적으로 40~60% 공간을 절약합니다. 예를 들어 함수 인덱스 0~127은 1바이트면 충분하지만, 고정 4바이트 인코딩이라면 매번 4바이트를 소비해야 합니다.

## 요약 — 데이터 타입 핵심

- WASM은 **4가지 기본 타입**만 제공합니다 (설계적 결정 — 컴파일 대상, 검증 용이성, 네이티브 성능)
- 정수는 **LEB128 가변 길이 인코딩**으로 저장됩니다 (작은 수는 1바이트)
- f32/f64는 **IEEE 754** 표준을 따릅니다 (0.1+0.2 주의!)
- 타입 변환 시 **trap 가능성**에 주의하세요 (NaN, 무한대, 범위 초과)
- WASM은 **리틀 엔디언** 바이트 순서를 사용합니다 (x86, ARM과 동일)
- v128(SIMD) 타입으로 **벡터 연산**도 지원됩니다 (WASM 2.0+)
